# TarotAI 产品设计详情

本文档从产品管理视角阐述 TarotAI：主要功能为何存在、当前实现如何支撑它们、以及每个设计选择创造了怎样的用户或商业价值。

## 产品定位

TarotAI 定位为一款消费级塔罗伴侣，既不仅仅是卡牌数据库，也不仅仅是 AI 聊天产品。

产品结合了三个层次：

1. **有引导的仪式体验** — 用户选择占卜类型、描述或选择主题、抽牌、获得结果。
2. **可复用的学习工具** — 用户可以浏览完整的塔罗卡牌图鉴，学习正位和逆位含义。
3. **可变现的 AI 服务** — 用户可以消费积分获取个性化、针对具体问题的解读。

这种分层很重要，因为塔罗使用场景并非总是相同的。有些用户想要快速的自省式占卜。有些想学习卡牌含义。有些想要与自己真实个人问题相关的深度解读。TarotAI 支持所有三种场景，而不强迫每个用户走最昂贵或最依赖网络的路径。

## 这套设计强在哪里

TarotAI 比简单的塔罗卡牌应用或通用的 AI 聊天包装更强，因为产品各层相互增强：

| 优势 | 为什么重要 |
| --- | --- |
| **离线优先的价值** | 用户甚至可以在付费、创建账号或后端可用之前就获得完整的占卜体验。这更强是因为 `tarot-ai-generator` 预先生成丰富的卡牌与维度解读内容到本地配置数据库中，而不是每次占卜都依赖实时 AI。 |
| **结构化的塔罗仪式** | 产品保持了熟悉的塔罗流程：选择主题、抽牌、解读牌阵。AI 增强仪式，而不是用无结构的聊天框替代它。 |
| **双层解读体系** | 基础解读提供稳定、低成本的价值；AI 解读提供高级个性化服务。这创造了清晰的升级路径，而不会让免费用户感到被阻挡。 |
| **基于维度的推理** | 每张卡牌通过特定视角解读，使结果比通用卡牌描述更加贴切。 |
| **本地内容 + 实时 AI** | 捆绑内容提供可靠性；实时 AI 添加个性化。应用不完全依赖其中任何一方。 |
| **历史记录作为留存手段** | 已保存的占卜给用户回访的理由，可以比较过去的情况，将应用视为自省日记。 |
| **卡牌图鉴作为信任层** | 用户可以查看结果背后的卡牌含义，使离线和 AI 解读都不那么像黑箱。 |
| **积分与备用充值** | 产品可以通过 AI 使用变现，同时通过兑换码支持无法使用 Google Play 的用户。 |
| **匿名身份** | 用户可以立即开始使用，同时产品仍有足够的身份连续性来支持积分、购买和本地历史。 |
| **运营工具** | 管理后台为产品提供了客服支持、积分调整、订单审查和活动运营的实用路径。 |

最强的产品理念是**仪式、可靠性、个性化和运营**的结合。用户看到的是简单的塔罗体验，而底层系统将静态内容、用户数据、AI 成本、变现和管理清晰地分离开来。

## 为什么存在离线/基础解读

离线/基础解读是产品的低门槛入口。

### 用户侧原因

- **即时价值：** 用户无需付费、注册或等待 AI 服务即可完成占卜。
- **建立信任：** 用户可以在消费积分之前看到塔罗流程和卡牌含义。
- **网络韧性：** 当后端或网络不可用时，占卜仍然有用。
- **学习支持：** 用户可以按自己的节奏比较卡牌位置、正逆位含义和维度特定解读。

### 商业侧原因

- **降低首次会话流失：** 免费、即时可用的占卜降低了用户在理解产品之前就离开的概率。
- **清晰的升级路径：** 在基础解读之后，AI 解读成为一种增强而非必需。
- **降低 AI 成本暴露：** 并非每次探索性使用都需要调用 LLM。

## 离线/基础解读如何实现

移动端应用采用双本地数据库设计：

```text
捆绑配置数据库                   运行时用户数据库
assets/db/tarot_config.db   +   SQLite/tarot_user_data.db
只读塔罗内容                    用户历史与偏好
```

### 配置数据库

应用捆绑 `assets/db/tarot_config.db`，并在启动时将其复制到应用的 SQLite 目录中。该数据库包含产品的只读塔罗内容：

- 78 张塔罗牌；
- 卡牌图片路径；
- 牌阵；
- 解读维度；
- 正位和逆位解读；
- 维度特定的解读内容。

启动路径在允许应用继续之前验证必要的表是否存在。这防止了有问题的发布版本在用户不知情的情况下显示不完整的塔罗内容。

实现参考：

- `my-tarot-app/lib/database/connection.ts` — 复制并验证捆绑的配置数据库。
- `my-tarot-app/lib/services/CardService.ts` — 读取卡牌数据和本地化的卡牌名称。
- `my-tarot-app/lib/services/CardInterpretationService.ts` — 读取基础和维度特定的解读。
- `my-tarot-app/app/(reading)/draw.tsx` — 从本地卡牌数据中抽牌。
- `my-tarot-app/app/(reading)/basic.tsx` — 从本地解读构建基础占卜结果。

### 用户数据库

用户数据库单独创建为 `tarot_user_data.db`。它存储属于用户的数据：

- 占卜历史；
- 选择的语言偏好；
- 本地用户设置。

将用户数据与塔罗配置分离，允许应用在未来的版本中更新卡牌内容而不删除用户的历史记录。

## 为什么 `tarot-ai-generator` 强化了离线优先设计

离线优先不仅仅是本地缓存。TarotAI 的离线/基础解读更强，是因为 `tarot-ai-generator` 在移动端应用发布之前，将昂贵、可审查的 AI 工作转化为可复用的产品内容。

生成器从 SQLite 中读取塔罗卡牌、正逆位含义、维度和翻译，渲染特定语言环境的提示模板，将每种语言路由到配置的模型，并导出结构化的 JSON，这些 JSON 可以被审查并导入回 `tarot_config.db`。

```text
SQLite 塔罗内容
  → 卡牌 × 方向 × 维度生成任务
  → 特定语言环境的提示与模型路由
  → 包含失败记录和模型元数据的结构化 JSON
  → 审查/导入维度解读
  → 捆绑的移动端配置数据库
  → 设备上的离线/基础解读
```

### 生成器优势

| 生成器设计 | 离线优先优势 |
| --- | --- |
| **批量卡牌 × 维度生成** | 应用可以附带许多预写的解读，使离线解读感觉丰富，而非像一个微小的静态查找表。 |
| **提示模板控制** | 产品语调可以在 `prompt_template.txt` 和 `prompt_template.en.txt` 中一次性调整，然后一致地应用到所有生成的内容中。 |
| **批量运行前调试样本** | 团队可以在花费 token 进行完整维度生成之前，在小样本上测试提示质量。 |
| **多语言模型路由** | 不同语言环境可以使用不同的提供商、模型、温度、速率限制和批量大小。这使语言质量和成本处于可控状态。 |
| **支持断点续传的生成** | 已完成的卡牌/语言组合在重新运行时会被跳过，因此长时间的生成任务可以从中断中恢复，而不必从头开始。 |
| **失败列表与重试路径** | 缺失或失败的输出是明确的，使离线内容生产可审计，而非靠猜测。 |
| **结构化 JSON 输出** | 生成的内容包含卡牌上下文、维度上下文、模型元数据和结果，使人工审查和数据库导入更安全。 |
| **试运行导入支持** | 内容可以在写回 SQLite 之前验证，降低损坏捆绑配置数据库的风险。 |
| **问题驱动的生成路径** | 产品经理可以定义一个真实的用户问题，将其匹配到三个维度，并为该场景生成一套完整的可复用内容。 |

### 产品影响

这种设计使离线/基础解读成为真正的产品界面，而非降级页面。用户获得带有维度特定文本的即时解读，而业务端避免了每次有人试用应用时都支付 LLM 调用费用。实时 AI 路径则成为针对个人背景的高级层，而非解读价值的唯一来源。

生成器实现参考：

- `tarot-ai-generator/main.py` — CLI 模式：调试样本、维度生成、多语言维度、问题驱动生成。
- `tarot-ai-generator/services/generation_service.py` — 批量编排、断点续传行为、重试处理、结构化输出合并。
- `tarot-ai-generator/services/prompt_builder.py` — 本地化提示模板渲染。
- `tarot-ai-generator/services/model_router.py` — 每种语言环境的提供商/模型路由和速率限制。
- `tarot-ai-generator/data_loader.py` — 带语言环境回退的 SQLite 卡牌和维度加载。
- `tarot-ai-generator/scripts/import_dimension_results.py` — 试运行安全的导入回 SQLite 配置数据库。

移动端实现参考：

- `my-tarot-app/lib/database/user-db.ts` — 存储和查询用户历史与设置。
- `my-tarot-app/lib/services/HistoryService.ts` — 历史列表、详情、搜索、删除和统计行为。
- `my-tarot-app/lib/services/ReadingService.ts` — 保存已完成的占卜结果。

## 为什么存在 AI 解读

AI 解读是产品的高级解读层。

基础塔罗内容是可复用且稳定的，但它无法深入理解用户的具体问题。AI 解读通过同时使用用户的描述、抽到的卡牌和选定的维度来添加个性化。

### 用户侧原因

- **针对问题的解读：** 同一张卡牌在育儿、工作、感情、金钱或健康方面可能有不同的含义。
- **降低塔罗专业知识要求：** 用户不需要手动组合卡牌、牌阵位置、方向和个人的背景。
- **更有用的输出：** AI 可以产生整体摘要和实用见解，而非仅仅是孤立的卡牌含义。

### 商业侧原因

- **自然的变现方式：** AI 调用消耗成本，因此积分使用直接对应真实的变动成本。
- **价值差异化：** 基础解读提供基线；AI 解读提供高级体验。
- **运营控制：** 积分检查、交易日志和管理工具使 AI 使用可审计。

## AI 解读如何实现

AI 解读采用两步流程。

```text
用户描述
  → 分析意图并推荐维度
  → 抽牌
  → 生成个性化解读
```

### 第一步：分析用户的问题

用户写下问题或情况描述。应用将其发送到后端，后端请求 LLM 为三牌阵推荐三个解读维度。

实现参考：

- `my-tarot-app/app/(reading)/ai-input.tsx` — 验证 200 字输入并调用分析。
- `my-tarot-app/lib/services/AIReadingService.ts` — 发送 `POST /api/v1/readings/analyze`，附带语言环境和 JWT 头。
- `tarot-backend/app/services/reading_service.py` — 将 LLM 推荐转换为稳定的维度条目，并在分析失败时回退到默认维度。

### 第二步：生成最终解读

用户抽牌后，应用将卡牌、方向、位置、维度和原始描述发送到后端。后端调用 LLM 并返回：

- 每张卡牌的 AI 解读；
- 维度摘要；
- 整体总结；
- 关键洞察；
- 生成元数据。

实现参考：

- `my-tarot-app/app/(reading)/ai-result.tsx` — 构建卡牌载荷并渲染 AI 结果。
- `my-tarot-app/lib/services/AIReadingService.ts` — 发送 `POST /api/v1/readings/generate`。
- `tarot-backend/app/services/reading_service.py` — 规范化维度并构建最终解读响应。

## AI 提示设计理念

TarotAI 在两个地方使用提示：

1. **运行时 AI 解读提示** 在 `tarot-backend/app/services/llm_service.py` 中，用于分析用户问题并生成最终的付费 AI 结果。
2. **内容生成提示** 在 `tarot-ai-generator/prompt_template*.txt` 中，用于创建可复用的卡牌与维度解读内容，后续支撑离线/基础解读。

这些提示的设计是为了保护产品体验，而不仅仅是从 LLM 获取文本。

### 问题分析提示

分析提示要求模型选择一个主类别，然后为三牌阵生成三个相关方面。

产品理念：

- **一个类别保持解读聚焦。** 询问工作问题的用户不应收到一个工作维度、一个感情维度和一个通用运势维度，除非问题真正需要这样。单一类别创造连贯的解读框架。
- **三个方面匹配仪式。** 应用在此流程中始终抽取三张牌，因此提示强制生成恰好三个维度，与三个位置清晰对应。
- **因果递进使结果具有结构感。** 提示要求描述从根本原因到当前状态再到下一步或可能结果的发展方面。这给用户一个叙事，而非三个不相关的标签。
- **简短的统一摘要帮助下游一致性。** 后端可以将一个简洁的主题传递到生成和分析中，而非仅依赖原始用户文本。
- **回退维度仍然可能。** 如果 LLM 失败或返回不可用的数据，后端可以回退到默认的三牌维度，而不中断产品流程。

### 最终解读提示

最终提示包含用户问题、抽到的卡牌、卡牌方向、维度以及卡牌到维度的映射，然后要求严格的 JSON 响应。

产品理念：

- **输出必须可机器读取。** 应用需要 `card_interpretations`、`overall_summary` 和 `insights` 作为独立的 UI 区域。JSON 防止移动端客户端解析自由格式的散文。
- **精确的卡牌 ID 防止 UI/数据不匹配。** 提示明确告诉模型不要重新编号或编造卡牌 ID，因为结果必须附加到用户实际抽到的卡牌上。
- **一张卡牌映射一个维度。** 这使解读易于浏览，防止一张卡牌过度解释所有可能的主题。
- **整体总结创造收束感。** 用户在阅读单张卡牌后需要最终的综合；否则结果感觉像是分离的碎片。
- **可操作的洞察使 AI 结果值得付费。** 提示拒绝模糊的陈词滥调，要求实用的收获。
- **特定语言环境的响应保持产品质量。** 后端构建特定语言的提示，并通过 API 传递语言环境，使生成的解读匹配用户的语言设置。

### 离线内容生成提示

生成器提示为特定的卡牌、方向、类别和方面创建可复用的解读内容。

产品理念：

- **传统象征意义锚定内容。** 提示从卡牌名称、方向、核心含义和详细注释开始，使生成的文本保持与塔罗的连接，而非变成通用建议。
- **维度聚焦使离线解读感觉个性化。** 即使没有实时 AI，同一张卡牌也可以针对情感、事业、健康、财富或决策主题进行不同解读。
- **专业但亲切的语调适合消费级应用。** 措辞要求普通受众能理解的指导，避免仅限专家理解的塔罗术语。
- **神秘感加实用指导保护塔罗氛围。** 提示保持自省、神秘的语调，同时仍给出用户可以付诸行动的建议。
- **没有具体日期或时间线使内容保持长青。** 离线内容可能在捆绑数据库中保留很长时间，因此避免具体日期防止过时或错误精确的预测。
- **没有标题或项目符号使内容易于嵌入。** 移动端 UI 可以将生成的段落直接放入结果卡片中，无需清理。

### 为什么提示避免过度具体的预测

TarotAI 定位为自省和指导产品，而非确定性的算命引擎。提示有意偏好主题性、抽象性和支持性的语言，而非精确预测。这有三个好处：

- 降低了做出不负责断言的风险；
- 使解读在不同现实生活场景中都保持有用；
- 让用户将塔罗视为决策支持的视角，同时对自己选择保持主导权。

### 积分模型

产品在进入 AI 解读之前检查用户是否有足够的积分。当前移动端流程预期需要两个积分，因为分析和生成是两个独立的付费 LLM 步骤。

产品收益：

- 用户理解 AI 解读是高级服务；
- 失败的 AI 调用不应消耗积分；
- 运营人员可以通过后端交易和管理工具审计积分使用。

## 为什么占卜流程被拆分为步骤

占卜流程被有意结构化，而非使用单一的聊天框。

```text
选择占卜类型 → 选择主题或描述问题 → 抽牌 → 阅读结果
```

这种结构赋予应用塔罗特定的身份：

- 用户仍然执行抽牌仪式；
- 产品可以结合随机性、牌阵位置和解读数据；
- AI 增强塔罗流程，而非用通用聊天替代它；
- 每个步骤都有明确的成功状态和错误状态。

对于离线/基础解读，用户选择一个主题组。对于 AI 解读，用户的问题被分析为推荐的维度。两条路径随后共享同一个抽牌界面。

## 占卜历史设计

占卜历史将一次性占卜转变为持续的自省产品。

### 保存了什么

每次完成的占卜存储：

- 用户 ID；
- 时间戳；
- 牌阵 ID；
- 抽到的卡牌 ID；
- 解读模式（`default` 或 `ai`）；
- 语言环境；
- 完整的解读结果 JSON。

实现参考：

- `my-tarot-app/lib/database/user-db.ts` — 插入带 `interpretation_mode`、`locale` 和序列化结果的历史记录。
- `my-tarot-app/lib/services/HistoryService.ts` — 支持列表、详情、筛选、搜索、删除、最近历史、日期范围和统计。
- `my-tarot-app/components/history/` — 历史列表和详情 UI 组件。

### 产品收益

- 用户可以回看过去的问题，比较情况如何变化。
- AI 解读感觉更持久，因为结果不会在会话结束后丢失。
- 历史记录增加了回访使用，而无需正式账号。
- 语言环境随结果一起存储，使过去的解读在语言更改后仍然可理解。

## 卡牌图鉴设计

卡牌图鉴是产品的学习和信任层。

它提供：

- 全部 78 张塔罗牌；
- 大阿卡那和小阿卡那筛选；
- 卡牌图片；

- 卡牌详情支持更好地理解离线和 AI 解读。

## 后端变现与控制设计

后端是付费 AI 使用的控制层。它不仅暴露解读 API；它将身份、余额、支付、兑换码、Google Play 验证、交易、订单和管理操作连接成一个可审计的系统。

```text
匿名用户 / installation_id
  → 用户余额
  → AI 解读积分检查
  → Google Play 或兑换码积分获取
  → 购买记录
  → 积分交易
  → 管理仪表板与客服工具
```

### 为什么后端控制很重要

- **AI 成本在服务端强制执行。** 解读 API 在 LLM 调用之前检查余额，并仅在成功分析或生成之后扣减积分。
- **支付变得可审计。** Google Play 购买和兑换码领取都创建购买记录和积分交易。
- **多个充值渠道共享一个余额。** Google Play、兑换码和管理员调整都更新同一个用户余额模型。
- **客服支持不需要数据库访问。** 管理 API 暴露用户查找、积分调整、订单审查、兑换码管理和导出。
- **运营可以看到渠道表现。** 仪表板逻辑区分 Google Play 订单、兑换码订单、活跃兑换码、待处理订单和最近活动。

### Google Play 验证路径

Google Play 路径在授予积分之前，通过 Google Play Developer API 验证购买令牌。

产品控制：

- 服务账号初始化是显式的，可以通过配置禁用；
- 购买令牌在本地履约之前与 Google 核对；
- 已处理的购买令牌返回成功而不授予重复积分；
- 产品 ID 映射到积分数量；
- 购买记录存储平台、订单 ID、积分、金额、货币、令牌和完成状态；
- 成功验证后可选将邮箱绑定到匿名用户；
- 购买可以在 Google Play 中消耗并在本地标记。

实现参考：

- `tarot-backend/app/api/payments.py` — `/api/v1/payments/google/verify`、`/google/consume` 和 Google webhook 入口。
- `tarot-backend/app/services/google_play.py` — Google Play 令牌验证、重复令牌处理、积分授予、购买记录和消耗。
- `tarot-backend/app/schemas/payment.py` — 包含 `installation_id`、`product_id`、`purchase_token` 和可选 `email` 的购买验证请求/响应模型。

### 兑换码路径

兑换码是第二个变现和运营渠道。当 Google Play 不可用、积分在商店外销售或分发、或客服需要补偿用户时，它们非常有用。

产品控制：

- 兑换码使用安全的随机生成并避免易混淆字符；
- 批次支持活动追踪；
- 每个兑换码有积分数量、状态、可选的过期时间、使用的用户和使用时间戳；
- 兑换码信息可以在使用前查询；
- 每日使用限制减少滥用；
- 成功兑换同时创建购买记录和积分交易。

实现参考：

- `tarot-backend/app/api/payments.py` — `/api/v1/payments/redeem` 和 `/redeem/info`。
- `tarot-backend/app/utils/redeem_code.py` — 安全兑换码生成、批次 ID、验证、每日限制和批次统计。
- `tarot-backend/app/models/payment.py` — `RedeemCode` 和 `Purchase` 数据模型。

### 积分账本与余额安全

积分不仅仅是用户身上的一个数字。后端维护一个余额表和一个交易账本。

产品控制：

- `user_balance` 存储当前余额和乐观锁版本；
- `credit_transactions` 记录每一笔赚取、消费、退款或管理员调整；
- 每笔交易记录变更后的余额、引用类型、引用 ID、描述和时间戳；
- 用户总计追踪累计购买和累计消费的积分；
- 余额不足时以需要付款的响应阻止付费 AI 调用。

实现参考：

- `tarot-backend/app/services/user_service.py` — 用户创建、余额查询、乐观锁余额更新、交易创建和管理员调整。
- `tarot-backend/app/models/user.py` — `User` 和 `UserBalance`。
- `tarot-backend/app/models/transaction.py` — 积分交易账本。
- `tarot-backend/app/api/readings.py` — AI 分析/生成调用的服务端余额检查和成功后扣减。
- `tarot-backend/app/api/users.py` — 用户余额、交易历史、统计和积分消费 API。

### 管理与仪表板控制

管理界面将支付和积分操作转化为可管理的产品工作流。

产品控制：

- 用户列表可按安装 ID、邮箱、邮箱状态、积分余额和日期范围筛选；
- 用户详情包含余额、总计和最近交易及平台与订单上下文；
- 管理员可以为客服、纠正、促销或退款调整积分；
- 订单列表可按平台、状态、安装 ID、邮箱、订单 ID 和日期范围筛选；
- 订单详情显示关联的积分交易；
- 兑换码管理支持列表、生成、状态更新、批次筛选和导出；
- 仪表板指标追踪用户数、活跃用户、售出积分、订单数、平台分布、待处理订单和活跃兑换码。

实现参考：

- `tarot-backend/app/api/admin.py` — 管理员用户、订单、购买和兑换码 API。
- `tarot-backend/app/services/dashboard_service.py` — 运营指标、平台分布、最近活动和系统状态。

### 产品影响

这个后端控制层使产品更强，因为变现没有分散在客户端中。移动端应用可以保持简洁，而后端处理支付信任、余额安全、审计记录、备用渠道和运营恢复。

## 积分、兑换码与购买渠道

积分用于控制付费 AI 使用。

### 为什么使用积分

- 它们将应用商店购买包与单次 AI 调用解耦。
- 它们让产品支持多种获取渠道。
- 它们使促销、手动发放和客服支持更容易。
- 它们让用户在执行高级操作之前看到可见的余额。

### 已支持或计划中的渠道

- **Google Play IAP：** 当 Android 和 Google Play 服务可用时使用。
- **兑换码：** 为无法使用 Google Play 或需要手动发放积分的用户提供备用方案。
- **管理员调整：** 运营人员可以为客服或运营目的调整用户积分。

实现参考：

- `my-tarot-app/app/(reading)/type.tsx` — AI 解读前检查积分余额。
- `my-tarot-app/components/settings/RechargeSection.tsx` — 余额、Google Play 购买区域和兑换码输入。
- `tarot-backend/app/api/payments.py` — 前端支付和兑换相关 API。
- `tarot-backend/app/services/google_play.py` — Google Play 购买验证。
- `tarot-admin-web/` — 用户、订单、兑换码和仪表板的运营控制台。

### 产品收益

- AI 成本受积分约束。
- 不支持 Play 的用户仍有充值路径。
- 运营人员可以为报表区分 Google Play、兑换码和手动积分来源。
- 失败或不可用的商店流程可以回退到兑换码，而不阻塞产品。

## 匿名身份设计

TarotAI 避免强制注册。产品使用稳定的匿名安装身份和 JWT 认证。

### 产品原因

- 塔罗占卜通常是情感性的、低承诺的首次会话。
- 首次启动时注册会增加摩擦。
- 匿名身份对于一台设备上的积分、历史记录和购买验证已经足够。
- 当购买或客服流程需要时，可以添加可选的邮箱绑定。

实现参考：

- `my-tarot-app/lib/services/AuthService.ts` — 匿名身份和令牌存储。
- `tarot-backend/app/api/users.py` — 匿名用户注册。
- `tarot-backend/app/models/user.py` — 后端用户模型。

## 管理后台设计

管理后台的存在是因为变现的 AI 产品需要运营可见性。

核心运营需求：

- 查找用户；
- 查看和调整积分；
- 生成和管理兑换码；
- 查看购买/订单来源；
- 监控仪表板指标；
- 发布或查看应用发布元数据。

产品收益：

- 客服操作不需要直接访问数据库；
- 积分和购买行为可以被审计；
- 兑换活动可以在不更改移动端应用的情况下管理；
- 产品指标可以指导未来的优化。

## 为什么这套架构对产品有利

| 设计选择 | 产品收益 |
| --- | --- |
| 离线/基础解读 | 免费、快速、有韧性的首次体验。更强是因为 `tarot-ai-generator` 预先生成维度特定内容，在支付、网络或实时 AI 不可用时仍能工作。 |
| AI 解读作为高级层 | 值得消费积分的个性化价值。更强是因为它升级了现有的塔罗流程，而非替代它。 |
| 基于维度的提示 | 更连贯的解读。更强是因为每张卡牌都有明确的分析角色，最终结果不是通用散文。 |
| 双本地数据库 | 应用内容可以更新而不危及用户历史。更强是因为产品内容和个人数据有不同的生命周期。 |
| 占卜历史 | 将一次性仪式转变为可复用的自省工具。更强是因为留存来自用户自己的过往占卜。 |
| 卡牌图鉴 | 建立学习价值和对解读体系的信任。更强是因为用户可以验证每次解读背后的词汇。 |
| 多语言资源 | 使产品更容易跨市场分享和扩展。更强是因为 UI、内容和 AI 输出可以跟随用户的语言。 |
| 后端支付控制 | 集中管理 Google Play 验证、兑换码、余额更新、订单记录和积分交易。更强是因为客户端不决定支付信任或积分履约。 |
| 积分与兑换码 | 支持变现、促销和备用充值路径。更强是因为支付失败不完全阻塞变现。 |
| 匿名身份 | 减少入门摩擦，同时保持足够的连续性。更强是因为首次会话保持轻量，而后端控制仍将积分和订单附加到稳定的安装 ID。 |
| 管理后台 | 赋予运营人员对用户、积分、订单、兑换码批次和指标的控制。更强是因为客服和活动不需要直接的数据库操作。 |

## 已知产品边界

- 离线/基础解读使用捆绑内容。它可靠但不对自由形式的用户问题进行个性化。
- AI 解读需要后端可用、积分和 LLM 提供商配置。
- Google Play 购买依赖 Android 原生构建支持和 Play 服务可用性。
- 离线历史目前仅存在于本地；完整的跨设备同步应被视为未来的产品工作，除非明确实现。
- 公开文档应保持英文和可安全分享。
